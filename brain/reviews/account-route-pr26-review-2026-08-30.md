## Verdict summary
The E→S rotation **signing shape is correct** (verified byte-for-byte against the Solidity `rotateMember` digest), the Pimlico-paymaster write path, route registration, CTA gating, storage helpers and humanWallet refactor all satisfy the contract. The **CRITICAL SAFETY guarantee ("the answer must never be orphaned") is NOT fully met**: two code paths can lose the respondent's nilDB records while still wiping `bootstrapE` / setting `anchor_address`. These are **BLOCKING** and must be fixed before merge.

## BLOCKING issues

1. **Delete-before-recreate migration ordering can orphan the answer.** In `migrateRecordsToDerivedLeaf`, every record is **deleted** under E (account-ctrlr.ts:241-248) *before* it is **recreated** under S (account-ctrlr.ts:267-276). If `createData` throws (or the app crashes between the delete and recreate loops), the records are already removed from E and never present under S — the answer is lost. The migration's own `catch` (account-ctrlr.ts:279-282) correctly returns `{ok:false}` so the controller keeps `bootstrapE` and skips the anchor, but the **nilDB data is already gone from E** — the localStorage fail-safe does not protect the actual records. The test `"keeps E when recreating records under S throws"` (account-ctrlr.test.ts) actually demonstrates this: `deleteOwnedData` resolves ok (delete commits), then `createData` rejects (recreate fails). Fix: recreate under S first, verify success, only then delete under E (a failed delete then leaves a harmless duplicate in E, never an orphan).

2. **`listOwnedBySurvey` swallows listing errors as `[]` ⇒ false "successful" migration ⇒ orphan.** The shared migration primitive catches all errors and returns `[]` (nilldb.user.service.ts:211-213). `migrateRecordsToDerivedLeaf` treats `records.length === 0` as a successful no-op migration (account-ctrlr.ts:256-259) and returns `{ok:true}`. So if the nilDB *list* fails (transient nilDB error, network), the flow believes there are zero records to move, proceeds to **wipe `bootstrapE` and set `anchor_address` (account-ctrlr.ts:210-212) while every real answer remains stranded under E's now-unrecoverable key → all answers orphaned.** Fix: have the migration surface a distinct "couldn't enumerate records" failure instead of a silent `[]`/success.

3. **On-chain rotate runs before the nilDB migration, so a migration failure still moves on-chain/Lit access off E.** `rotateMember` is written at account-ctrlr.ts:183-192; the nilDB migration runs afterward at :203. Because E is removed from `poolMembers` on-chain first, after a migration failure E is no longer a pool member and fails the Lit `isPoolMember` access condition — so the "kept" E cannot actually read its own retained records. The user-facing message "Nothing was wiped — your existing access is unchanged" (account-ctrlr.ts:131-134) therefore overstates the safety of the failure path. Ideally the nilDB move completes while E is still a member (see also #1), and the failure copy should not promise "unchanged access."

## Non-blocking notes
- `anchor_address` stores the raw email string rather than an address (account-ctrlr.ts:212 / storage.ts:101-106). Fine as a "device secured" flag (and the CTA gating only checks `undefined`), but the field name is slightly misleading next to the RFC's terminology.
- If `deleteOwnedData` fails *after* a successful recreate, the record exists under both E and S (duplicate, not orphaned) — acceptable, but the code makes no attempt to cleanup duplicate; worth a note in a follow-up.
- `chainId` falls back to hardcoded `8453` (base mainnet) at account-ctrlr.ts:180; correct for the shipped network but would silently mismatch on any non-base chain (replay/binding mismatch). Consider deriving from the active chain rather than a literal default.
- The status/anchor field reuses `this.statusMessage`, so the CTA/status copy re-renders the whole template (renderTemplate) on each interaction — functionally fine, mildly redundant.
- Non-blocking: `secureWithEmailWallet` re-derives S on every recover attempt even when S is already persisted (`derivedS`), doing a fresh WaaP login; acceptable per design but not optimized for same-device Case-1.
